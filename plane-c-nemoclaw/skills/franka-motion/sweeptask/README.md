# 任務檔格式

一個任務一個 `.md`，檔名（去掉副檔名）就是使用者說「執行 X」時的那個 X。

刻意用散文而不是 JSON/YAML：Agent 是直接讀這份文件然後用 MCP 工具執行的，
自創一套 DSL 只會多一層要它翻譯的東西，翻錯了還很難查。

## 建議的段落

```markdown
# <名稱>

<一句話說明這個任務在展示什麼>

## 前提
<需要什麼樣的機器人。沒有特殊需求就寫「任何有 revolute 關節的手臂」>

## 動作
<照 SKILL.md 的標準流程第 8 步要做什麼，寫清楚就好>

## 回報
<這個任務特別要讓使用者看到什麼>
```

**沒有 `robot` 段。** 機器人是執行時參數，由使用者在 prompt 裡指定，
預設 `frankapanda`。任務檔寫死機器人就失去通用性了。

## 寫的時候注意

### 不要重複 SKILL.md 已經寫過的東西

`stop` 先行、`position_source` 檢查、單位、夾極限、完整姿勢——那些是通用程序，
寫在這裡只會兩邊不同步。

### 用關節的「角色」，不要用名字

寫「所有 revolute 關節」、「中段那個關節」、「所有 prismatic 關節」，
**不要寫 `panda_joint4` 或 `elbow_joint`**。名字換一台機器人就全錯。

需要挑特定關節時，用 `get_robot_info` 的順序來指定位置，例如
「revolute 關節裡索引位於中間的那一個」。

### 幅度用比例，而且要有絕對上限

不同機器人的極限差非常多。Franka 的關節多在 ±2.9 弧度，UR 的手腕常常是 ±2π。
同樣的「行程 25%」，在後者上是接近半圈的猛甩。

比例之外一定要再套一個絕對上限（SKILL.md 的預設是 1.0 弧度）。

### 增益用相對值，不要寫死數字

drive 增益的尺度跟機器人、跟資產作者的習慣有關，差一個數量級是常事。
寫死一組數字換一台機器人可能兩輪都追得上、或兩輪都追不上，對比就消失了。

正確做法：先 `get_joint_config` 讀現在的值，再以它為基準乘除。
**還原時也是寫回讀到的那個值，不要寫回文件裡的常數。**

### 前提不符要能偵測

任務需要特定條件（例如夾爪）時，在「前提」段寫清楚怎麼檢查，
以及檢查失敗時要回報什麼。不要讓 Agent 硬跑然後失敗。

### 只寫要做什麼，不要寫怎麼呼叫工具

Agent 知道工具怎麼用。文件寫「送目標並讀回」就夠了，
不用寫 `set_joint_positions(prim_path=..., joint_positions=[...])`。

## 換一台機器人

**不用改任何檔案。** 使用者在 prompt 裡說「用 UR10 執行 joint_sweep」即可。

如果某個任務就是只在特定機器人上有意義，把條件寫在「前提」段，
讓 Agent 自己判斷並回報，而不是寫死機器人名稱。
